# 13. 보안·빈틈 점검

> 평가 대비용. 보안 검토(1~6절)와 **침투 테스트(7절)** 를 함께 둔다. 평가에서는 "기능이 되나" 보다 **"빈틈을 찔렀을 때 버티나"** 를 본다. 평가자가 찔러볼 만한 지점을 미리 찾아 **대응됨 / 미대응 / 판단(대응하지 않기로 함)** 으로 정리한다.
> 대응하지 않기로 한 것은 근거를 남긴다 — 그래야 빈틈이 아니라 **판단**이 된다.
> **진행하면서 계속 추가한다.** 실서버 테스트·코드 리뷰·새 기능에서 발견하면 해당 표와 [8. 갱신 기록](#8-갱신-기록)에 적는다.
> 관련 문서: [03-api.md](03-api.md)(결과 코드·인증) · [12-decisions.md](12-decisions.md)(결정 근거) · [11-open-issues.md](11-open-issues.md) · [07-verification.md](07-verification.md)

범례 — 상태: ✅ 대응됨 · ⚠️ 미대응 · 📝 판단(대응하지 않기로 함, 근거 있음) · 🔍 확인 필요
위험도: **높음** 평가·운영에서 실제 피해 가능 · 중간 공격 표면이 넓어짐 · 낮음 관례 수준

## 2. 알고 있는 한계 (문서에 근거를 남긴 판단)

| # | 한계 | 판단·근거 | 보완 |
|---|---|---|---|
| L01 | 관리자 주소가 프론트 번들에 들어 있다 | 주소 숨김은 무작위 탐색을 줄이는 장치다. 실제 방어는 서버 `require_admin`(403) | 비관리자에게는 없는 주소와 같은 404 화면 ([05-ui-ux.md](05-ui-ux.md) 화면 5) |
| L02 | 토큰을 localStorage 에 저장 → XSS 가 있으면 탈취 가능 | 새로고침 시 로그인 유지 요구, 프론트·백엔드 다른 도메인이라 쿠키 방식의 제약 ([12-decisions.md](12-decisions.md) 4절) | HTML 해석 금지, access 15분, refresh 회전, 로그아웃 시 서버 폐기 |
| L03 | access 토큰은 만료 전에 취소할 수 없다 | 저장하지 않고 서명으로 확인하는 JWT 의 일반적 특성 | 수명 15분으로 짧게 |
| L04 | 응답은 성공·실패 모두 **HTTP 200**, 결과는 body `code` | 프론트가 한 곳에서 판단하고 "서버가 처리한 실패"와 "서버에 닿지 못한 실패"를 구분 ([12-decisions.md](12-decisions.md) 6절) | 대가: 네트워크 탭·Railway 지표에 실패도 200 으로 보인다 → 서버 로그·관리자 화면에 코드가 남는다. REST 관례와 다르므로 평가 때 근거 설명 준비 |
| L05 | CORS 는 브라우저만 지키는 규칙 | curl·다른 서버는 CORS 와 무관하게 API 를 부를 수 있다 | 실제 방어는 인증(JWT). CORS 는 다른 사이트가 사용자 브라우저로 우리 API 를 부르는 것을 막는 용도 |
| L06 | bcrypt 는 앞 72바이트만 쓴다 | 한글 약 24자. 실사용 문제는 거의 없다 | 해시·검증 모두 같은 규칙으로 자른다 |
| L07 | 관리자 화면 주소에 사용자 번호가 보인다 (`?user=2`) | 번호를 알아도 조회는 서버 `require_admin` 이 막는다 — 남의 번호로 바꿔 보는 공격(IDOR)은 권한 검사로 막는 것이지 번호를 숨겨서 막는 것이 아니다. 이 주소를 보는 사람은 이미 모든 사용자를 볼 수 있는 관리자다. 드러나는 것은 가입 순서·대략의 사용자 수 정도 | 일반 사용자 API(`/api/me/*`)는 번호를 받지 않고 토큰의 사용자로만 조회. 공개 번호(UUID) 도입은 이득이 작아 하지 않음 |
| L08 | 가입·로그인 때 Chrome 이 "비밀번호가 유출되었다"고 경고할 수 있다 | Chrome 비밀번호 진단이 **입력한 비밀번호 자체**가 알려진 유출 목록에 있는지 본 것이다. 우리 사이트·HTTPS 와 무관(테스트용 흔한 비밀번호에서 발생) | 비밀번호 규칙은 8자 이상만. 흔한 비밀번호 차단은 하지 않음 |

## 3. 대응된 것 (평가 때 근거로 말할 수 있는 것)

| 항목 | 내용 | 확인 |
|---|---|---|
| 인증 | 토큰 **서명** 확인(위조 거부) → 허용 알고리즘 HS256 고정(`none` 공격 차단) → `exp`·`sub` 필수 → 만료 확인 → **DB 에 사용자가 실제로 있는지** 확인 | 2026-10-06 배포 A5 |
| 권한 | role 을 토큰에 넣지 않고 **요청마다 DB 에서 확인**(권한 회수 즉시 반영). 관리자 라우터 전체에 한 번에 적용해 경로마다 빠뜨릴 위험이 없다. 401(누군지 모름)과 403(권한 없음)을 구분 | 2026-10-06 배포 A6 |
| 권한 확인 순서 | 관리자 API 는 권한(403)을 먼저 본다 → 비관리자에게 "그 사용자가 있는지(404)" 조차 알려 주지 않는다 | 배포 A6 |
| 남의 데이터 | 서버는 토큰의 사용자 id 만 쓴다. 클라이언트가 보낸 사용자 id 는 쓰지 않는다 | 로컬 백엔드 2026-09-29 (계정 분리) |
| 비밀번호 | bcrypt `$2b$`, 비용 12, **해시마다 새 128비트 salt**(해시 문자열 안에 저장). 없는 이메일로 로그인해도 비교를 한 번 해서 응답 시간으로 계정 존재를 알 수 없다 | 코드 리뷰 |
| refresh 토큰 | 384비트 무작위 값, DB 에는 **SHA-256 해시만**, 재발급마다 회전, 삭제+발급을 한 트랜잭션, 동시 사용 시 한쪽만 성공, 만료 행 매일 정리 | 코드 리뷰, 로컬 백엔드 재발급 |
| 서명 키 | `JWT_SECRET_KEY` 는 환경변수, 코드에 기본값 없음, **비어 있으면 서버 시작 거부** | 코드 리뷰 |
| 입력 검증 | 질문 1~1000자, 이메일·비밀번호(8자+)·닉네임(1~20) 서버 검증 → 422. 프론트 검증은 보조 | 백엔드 테스트 |
| 오류 응답에 내부 정보 없음 | 깨진 JSON·잘못된 타입 → `code: 422` "입력값이 올바르지 않습니다.", 서명 없는 토큰(`alg: none`) → `401`, `TRACE` → `405`, 서버 오류 → `500` "서버 내부 오류가 발생했습니다." — 스택·SQL·경로·필드 상세가 응답에 나오지 않는다 | 로컬 백엔드 2026-10-07 |
| SQL 주입 | ORM(SQLAlchemy)이 매개변수로 처리 | 코드 리뷰 |
| XSS | AI 답변을 포함해 사용자 입력을 HTML 로 해석하지 않음, `dangerouslySetInnerHTML` 없음 | 프론트 테스트 |
| 비밀값 | `COPA_API_KEY` 는 서버에만, 프론트 번들에 없음, `.env` 는 커밋 안 함 | 2026-10-06 배포 A7 |
| CORS | `CORS_ORIGINS` 에 등록한 주소만 허용(`*` 미사용), 쿠키 미사용, 메서드·헤더 최소 | 2026-10-06 배포 A2·A3 |
| 오류 응답 | 404·405·422·500 도 같은 봉투, 내부 오류 내용(스택)을 밖에 노출하지 않음 | 배포 A4 |
| 감사 로그 | 관리자 API 호출 `admin_access`, 비관리자 시도 `admin_forbidden` | 2026-10-06 배포 A6 |
| 로그 민감정보 | 서버 로그에 비밀번호·토큰 미기록 | 백엔드 테스트 |
| 검색 노출 | 로그인 필요 화면·관리자·404 는 `noindex`, robots.txt 에 관리자 주소를 적지 않음 | 2026-09-29 배포 |

## 4. 결과 코드 점검

HTTP 표준(RFC 9110)의 뜻에 맞게 정했는지 확인했다 (2026-10-06). 정의는 [03-api.md](03-api.md) 0절.

| code | 쓰는 상황 | 표준의 뜻 | 판단 |
|:-:|---|---|:-:|
| 200 | 조회·처리 성공 | 성공 | ✅ |
| 201 | 회원가입 성공 | 새 자원 생성 | ✅ |
| 401 | 토큰 없음·만료·위조 / 로그인 실패 | 인증 필요(누구인지 모름) | ✅ 로그인 API 의 401 은 재발급하지 않고, 그 외 API 의 401 은 재발급을 시도하도록 프론트가 구분 |
| 403 | 일반 사용자가 관리자 API 호출 | 권한 없음(누구인지는 앎) | ✅ |
| 404 | 없는 경로, 없는 사용자·request_id | 대상 없음 | ✅ |
| 405 | 정해진 메서드가 아님 (예: `/api/chat` 을 GET) | 메서드 허용 안 됨 | ✅ |
| 409 | 이메일 중복 가입 | 현재 상태와 충돌 | ✅ (가입 여부 노출은 S09) |
| 422 | 입력값 검증 실패 | 형식은 맞지만 내용이 처리 불가 | ✅ FastAPI 기본. 400 도 쓰이지만 둘 다 맞음 |
| 500 | 서버 내부 오류 | 서버 잘못 | ✅ |
| 502 | AI API 호출 실패 | 중간 서버가 뒤쪽 서버에서 잘못된 응답을 받음 | ✅ 우리 서버가 AI 를 대신 부르는 중간 서버라 정확 |
| 504 | AI API 시간 초과 | 중간 서버가 뒤쪽 서버 응답을 기다리다 시간 초과 | ✅ 502 와 나눠 안내 문구를 다르게 고른다 |
| (429) | — | 요청이 너무 많음 | 미정의. S01·S02 를 대응하면 추가 |

## 5. 확인 방법 (직접 해 볼 수 있는 것)

배포된 **프론트 사이트**의 개발자도구 Console 에서 실행한다 (프론트 주소에서 실행해야 CORS 가 통과).

```js
// 토큰 없이 — 모두 code: 401
const API = 'https://<백엔드 공개 도메인>'
const show = async (label, res) => console.log(label, res.status, await res.json())
show('POST /api/chat', await fetch(`${API}/api/chat`, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ message: '안녕' }) }))
show('GET /api/me/chats', await fetch(`${API}/api/me/chats`))
show('GET /api/admin/stats', await fetch(`${API}/api/admin/stats`))
```

```js
// 일반 사용자로 로그인한 같은 탭에서 — 관리자 API 5개 모두 code: 403
const token = localStorage.getItem('auth:access_token')
const get = async (path) => console.log(path, (await (await fetch(`${API}${path}`, { headers: { Authorization: `Bearer ${token}` } })).json()).code)
for (const p of ['/api/admin/stats', '/api/admin/users', '/api/admin/users/1/chats', '/api/admin/failures', '/api/admin/requests/test-id/logs']) await get(p)
```

- 주소창으로 POST API 를 열면 GET 이라 `code: 405` 가 맞다 (메서드 확인이 인증보다 먼저)
- 감사 로그(`admin_forbidden`)는 Railway 백엔드 Logs 탭에서 확인
- 출력이 401 이면 access 토큰 만료(15분) — 사이트에서 메뉴를 한 번 눌러 재발급 후 다시 실행

## 7. 침투 테스트 (공격자 입장에서 실제로 찔러 보기)

1~3절은 대부분 **코드를 읽고** 찾은 것이다. 이 절은 공격 요청을 **실제로 보내** 막히는지 확인한다.
뚫리면 1절에 S 번호로 올리고, 막히면 3절 "대응된 것"의 근거로 연결한다. 결과 칸이 비어 있으면 아직 해 보지 않은 것이다.

- **환경**: 로컬 = 로컬 백엔드·프론트, 배포 = Railway. 연속 요청(P15·P16)은 AI 비용·서버 부하가 있어 **로컬에서만** 한다
- **기록**: 결과 · 날짜 · 환경. 측정값(응답 코드·시간)을 함께 적는다

### 7-1. 새 공격 항목

| # | 공격 | 방법 | 기대 (막혔다고 보는 조건) | 환경 | 결과 |
|---|---|---|---|---|---|
| P01 | **XSS 실제 주입** | 질문·닉네임에 `<img src=x onerror=alert(1)>`, `<script>alert(1)</script>`, `javascript:alert(1)` | 챗 말풍선·내 대화 로그·관리자 목록과 상세·헤더 닉네임·시각 말풍선(`title`)에서 **글자로만** 보이고 실행되지 않음 | 로컬 | |
| P02 | **SQL 인젝션** | 관리자 검색 `q=' OR 1=1--`, 로그인 이메일 `' OR '1'='1` | 전체 행이 나오지 않고 DB 오류가 응답에 새지 않음 (ORM 바인딩) | 로컬 | |
| P03 | **LIKE 와일드카드 남용** | 관리자 검색 `q=%`, `q=_` | `%`·`_` 를 글자로 취급하는지 (전체가 나오면 이스케이프 필요) | 로컬 | |
| P04 | **토큰 내용 변조** | access 토큰 payload 의 `sub` 만 다른 번호로 바꾸고 서명은 그대로 | `code: 401` | 로컬 | |
| P05 | **다른 키로 서명한 토큰** | 임의 키로 같은 형식(HS256, `sub`·`exp`)의 토큰 생성 | `code: 401` | 로컬 | |
| P06 | **로그아웃 뒤 refresh 재사용** | 로그아웃 전 refresh 토큰을 복사 → 로그아웃 → `/api/auth/refresh` | `code: 401` (서버에서 폐기) | 로컬 | |
| P07 | **권한 상승 필드 끼워넣기** | 가입 본문에 `"role":"admin"` 추가 | 무시되고 `role=user` 로 생성 | 로컬 | |
| P08 | **로그인 후 이동 주소 조작 (오픈 리다이렉트)** | 로그인 화면으로 보낼 때 남기는 "원래 가려던 주소"에 `https://evil.example`, `//evil.example` 를 넣어 로그인 | 외부 사이트로 이동하지 않음 | 로컬 · 배포 | |
| P09 | **CORS 특수 Origin** | `Origin: null`, `Origin: https://<프론트 주소>.evil.com` (앞부분만 같은 주소) | 허용 헤더가 오지 않음 (배포 A3 은 완전히 다른 주소만 확인) | 배포 | |
| P10 | **배포 정보 노출** | 배포 프론트 `*.js.map`(소스맵), 백엔드 `/openapi.json`·`/redoc` | 소스맵 없음. API 명세 공개 여부는 S03 결정을 따름 | 배포 | |
| P11 | **로그 위조** | 이메일·닉네임에 줄바꿈(`\n`)과 가짜 로그 줄을 넣어 가입·로그인 | 서버 로그에 가짜 줄이 생기지 않음 (422 또는 한 줄로 기록) | 로컬 | |
| P12 | **특수 문자 입력** | 질문·닉네임에 제어 문자, 방향 바꾸는 문자(RTL), 이모지 1000개, 전각·제로폭 공백 | 화면 깨짐 없음, 1000자 제한·"공백만" 검사가 우회되지 않음 | 로컬 | |
| P13 | **클릭재킹 실제 시험** | 다른 페이지에서 `<iframe src="<배포 프론트>">` | 화면이 들어가지 않음 (S07 헤더 부재의 실제 영향 확인) | 배포 | |
| P14 | **HTTP 접속** | 배포 주소를 `http://` 로 열기 | HTTPS 로 넘어감 (HSTS 는 S07) | 배포 | |
